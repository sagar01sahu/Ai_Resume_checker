# ResumeRank: AI-Based Resume Matching & Candidate Ranking System

ResumeRank compares a batch of resumes against a Job Description (JD) and produces a ranked shortlist with an **explainable 0-100 match score** for every candidate.

- **Live demo:** https://resumerank-app-production.up.railway.app
- **Demo video:** https://drive.google.com/file/d/18HTIMT8ChogPjDGUsAXtwoewNfcPII4W/view?usp=sharing
- **Source code:** https://github.com/sagar01sahu/Ai_Resume_checker.git

> **Note:** All resumes in this repository are **synthetic** and generated by `scripts/generate_samples.py`. No real candidate data is used.

---

## 1. What it does

| Assignment module | What ResumeRank provides |
|---|---|
| **1. JD input** | Paste text or upload PDF/DOCX/TXT. Extracts required skills, nice-to-have skills, minimum years, education and title. |
| **2. Resume upload** | Batch upload of 10+ PDF/DOCX resumes. Extracts name, email, phone, skills, experience, education and projects. Per-file parse status. |
| **3. AI matching** | Overall score (0-100), matched and missing skills, experience evaluation, and semantic similarity beyond exact keywords. |
| **4. Ranking dashboard** | Sortable table with search, minimum-score filter and CSV export. |
| **5. Candidate analysis** | Extracted info, sub-score breakdown, matched/missing skills, experience comparison, and a plain-English explanation. |

**Extras:** live matching progress with cancel, adjustable scoring weights with rank-change arrows, side-by-side candidate comparison (up to 4), past screenings history, and a bias-awareness note on each candidate.

1. Open the live demo.

## 3. Architecture

```
React + Vite + Tailwind (served as static files by FastAPI)
        |  REST / JSON
FastAPI (Python 3.11)
  |-- parser.py     PDF/DOCX -> text (pdfplumber, PyMuPDF fallback, python-docx)
  |-- extractor.py  spaCy NER + PhraseMatcher + skills taxonomy + experience dedup
  |-- matcher.py    SentenceTransformer embeddings + deterministic scoring
  |-- explainer.py  rule-based explanation (+ optional Gemini narration)
        |
PostgreSQL 16 (JSONB for skills, experience, scores)
```

| Layer | Technology |
|---|---|
| Frontend | React 19, TypeScript, Vite, Tailwind CSS, TanStack Table |
| Backend | Python 3.11, FastAPI, Uvicorn, SQLAlchemy 2.0, Pydantic v2 |
| Parsing | pdfplumber (primary), PyMuPDF (fallback), python-docx |
| NLP | spaCy `en_core_web_md` (NER + PhraseMatcher) |
| Embeddings | `sentence-transformers/all-MiniLM-L6-v2` (384-dim, runs locally, no API key) |
| Database | PostgreSQL 16 (JSONB) |
| LLM (optional) | Google Gemini 2.5 Flash, only for JD structuring and explanation wording |
| Deployment | Docker (multi-stage), Railway, GitHub Actions CI |

**Design decision:** the score is computed by a deterministic formula. The LLM never decides or changes a score. Without a `GEMINI_API_KEY`, the whole app works offline with rule-based extraction and explanations.

## 4. Matching algorithm and scoring methodology

```
Final = 0.40 x Skill + 0.25 x Semantic + 0.25 x Experience + 0.10 x Education
```

Weights are configurable per request (the sliders in the UI) and are normalised to sum to 100%.

### 4.1 Skill score (40%)
1. Skills are normalised through a taxonomy of 30+ canonical skills with aliases (e.g. `Postgres`, `psql` -> **PostgreSQL**; `GitHub Actions`, `Jenkins` -> **CI/CD**).
2. Each JD skill is embedded and compared by cosine similarity with every candidate skill.
3. A JD skill counts as **matched** if there is an exact canonical match or the best cosine similarity is **>= 0.75**.
4. Required skills have weight **2**, nice-to-have skills weight **1**.
5. `Skill = (sum of matched weights / sum of all JD skill weights) x 100`. Skills below the threshold are reported as **missing**.

### 4.2 Semantic score (25%)
1. The resume is split into up to 8 chunks, so a long irrelevant section does not dilute a strong project section.
2. The JD and each chunk are embedded.
3. The score uses the **mean of the top 3** chunk-to-JD cosine similarities.
4. Raw MiniLM cosines rarely leave about 0.25 to 0.78, so the value is rescaled linearly from **[0.25, 0.78] to [0, 100]** and clipped.

### 4.3 Experience score (25%)
1. Work date ranges are converted to month indices, and lines about degrees or universities are ignored.
2. Overlapping ranges are merged (interval merging), so two concurrent roles are not double-counted.
3. If no date ranges exist, explicit mentions such as "5+ years" are used.
4. `Experience = min(candidate_years / required_years, 1) x 100`. Over-qualification is capped, not penalised.

### 4.4 Education score (10%)
- Degree tiers: PhD = 4, Master's = 3, Bachelor's = 2, Diploma = 1, none = 0.
- Base score: meets the required tier = 80, above = 95, below = 50, no degree found = 30.
- Field modifier when the JD asks for a technical field: +10 for a technical degree, -15 for a non-technical one.

### 4.5 Worked example (illustrative numbers)

JD: 6 required skills (weight 2 each), 1 nice-to-have (weight 1), 4 years required, bachelor's in a CS field.

| Component | Calculation | Score | Weight | Contribution |
|---|---|---|---|---|
| Skill | matched 5 required + 1 nice-to-have: (10 + 1) / 13 | 84.6 | 0.40 | 33.8 |
| Semantic | top-3 mean cosine 0.62: (0.62 - 0.25) / (0.78 - 0.25) | 69.8 | 0.25 | 17.5 |
| Experience | 3.5 / 4 years | 87.5 | 0.25 | 21.9 |
| Education | B.Tech CS: meets tier (80) + technical field (+10) | 90.0 | 0.10 | 9.0 |
| **Overall** | | | | **82.2** |

### 4.6 Explanations
- A rule-based explanation is always generated from the computed numbers: matched/missing skills, years vs. required, semantic strength, degree.
- If a Gemini key is set, the LLM only rewrites those exact facts into a short recruiter summary. The prompt forbids adding facts or changing scores.

### 4.7 Bias awareness
Name, email and phone are shown to recruiters but are **not** used in scoring or embeddings. Each candidate page shows a bias-awareness note.

## 5. API reference

Interactive docs are at `/docs`.

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/api/health` | Health and model status |
| GET | `/api/jobs` | List past screenings |
| POST | `/api/jobs` | Create a job from JD text (JSON) or a file (multipart) |
| DELETE | `/api/jobs/{id}` | Delete a screening and its candidates |
| POST | `/api/jobs/{id}/resumes` | Batch upload resumes |
| POST | `/api/jobs/{id}/sample` | Load the 12 synthetic sample resumes |
| POST | `/api/jobs/{id}/match` | Start matching as a background task |
| GET | `/api/jobs/{id}/status` | Poll progress and skipped files |
| POST | `/api/jobs/{id}/cancel` | Cancel a running match |
| GET | `/api/jobs/{id}/ranking` | Ranked list (supports `min_score` and custom weights) |
| GET | `/api/jobs/{id}/export` | Download the ranking as CSV |
| GET | `/api/candidates/{id}` | Full candidate analysis |

## 6. Database schema

| Table | Key columns |
|---|---|
| `job_descriptions` | `id`, `title`, `raw_text`, `parsed` (JSONB), `status_state` (JSONB), `created_at` |
| `candidates` | `id`, `job_id` (FK), `filename`, `name`, `email`, `phone`, `total_experience_years`, `skills`, `experience`, `education`, `projects` (JSONB), `parse_status` |
| `match_results` | `id`, `candidate_id` (FK, unique), `job_id` (FK), `overall_score`, `skill_score`, `semantic_score`, `experience_score`, `education_score`, `matched_skills`, `missing_skills` (JSONB), `explanation` |

The four sub-scores are stored separately, so the weight sliders recompute the ranking with simple arithmetic and no re-embedding.

## 8. Run locally

### Option A: Docker Compose (recommended)
```bash
cp .env.example .env
# optional: set GEMINI_API_KEY in .env (the app works without it)
docker compose up --build
```
Open http://localhost:8000 . Postgres is exposed on host port 5433.

### Option B: Manual
```bash
# Backend
cd backend
pip install -r requirements.txt
python -m spacy download en_core_web_md
export DATABASE_URL=postgresql://user:pass@localhost:5432/resumerank
uvicorn app.main:app --reload --port 8000

# Frontend (new terminal, project root)
npm install
npm run dev
```

### Environment variables
| Variable | Required | Purpose |
|---|---|---|
| `DATABASE_URL` | Yes | PostgreSQL connection string |
| `GEMINI_API_KEY` | No | Enables LLM JD extraction and explanation wording |
| `PORT` | No | Server port (default 8000) |

### Tests
```bash
cd backend
pytest -v            # alias normalisation, interval dedup, experience cap, ranking order
python evaluate.py   # end-to-end ranking across the 12 sample resumes
```

## 9. Deployment

The app is deployed on **Railway** as a Docker service with a managed PostgreSQL database.
- The Docker image bundles the React build, `en_core_web_md` and `all-MiniLM-L6-v2`, so startup needs no model downloads.
- Railway's injected `PORT` is read at runtime, and `GET /api/health` is used as the health check.
- `render.yaml` is also included for deploying to Render.
- GitHub Actions runs type-checking, the Vite build, `pytest` and the ranking evaluation on each push.

## 10. Engineering notes

- **Scanned PDFs:** pdfplumber falls back to PyMuPDF if fewer than 40 characters are found. If a PDF with pages still yields fewer than 30 characters, it is marked *Failed: scanned image* and skipped.
- **Overlapping jobs:** interval merging prevents inflated experience.
- **Deployment bug worth noting:** an unanchored `data/` entry in `.gitignore` and `.dockerignore` silently excluded `backend/app/data/skills_taxonomy.json`, so the app worked locally but crashed on Railway. Anchoring the entries to `/data/` fixed it.

## 11. Limitations

- No OCR: scanned or image-only PDFs are rejected, not read.
- English-language resumes only.
- Skill coverage depends on the taxonomy (30+ skills), so skills outside it can only be matched through embeddings.
- Scores are relative to a given JD and are meant to support a recruiter's decision, not replace it.
- Experience is estimated from date ranges found in the text, so unusual date formats may be missed.
- On a free hosting tier the first request after idle time can be slow.
